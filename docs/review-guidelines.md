# レビュー運用規約 v1

- 状態：採用（2026-10-31、プロジェクトオーナー承認）
- 起草：ちゃぴ子先生、オパ子先生
- 対象：AI Conversation Studio のプルリクエストのレビュー

## 1. 背景

このリポジトリでは、実装を Codex が担当し、ちゃぴ子先生（GPT）とオパ子先生（Claude）がレビューを担当する。
レビューはどちらもプロジェクトオーナーの GitHub アカウントを通じて投稿されるため、次の制約がある。

- PR の作成者とレビューの投稿者が同じアカウントになる。GitHub では自分の PR に `APPROVE` も `REQUEST_CHANGES` も付けられない。
- `main` にはブランチ保護を設定していない。GitHub のレビュー状態はマージをブロックしない。

そのため、GitHub のレビュー状態ではなく、**レビュー本文の判定**でマージ可否を伝える。

## 2. 規約

1. GitHub への投稿種別は原則 `COMMENT` とする。
2. 本文の冒頭に必ず総合判定を記載する。
   - `判定：Request changes（マージ前に修正必須）`
   - `判定：Approve 相当`
   - `判定：Comment（非ブロッキング）`
3. 個別の指摘には、重要度と対応期限を明記する。

   | 重要度 | 対応期限 |
   | --- | --- |
   | 🔴 Critical / 🟠 Major | マージ前に修正 |
   | 🟡 Minor | 後続の Slice で対応可能 |

4. レビュアー間で判定が異なる場合は、原則として厳しい判定を採用し、プロジェクトオーナーに判断材料を提示する。
5. 最終的なマージ判断はプロジェクトオーナーが行う。

## 3. 判定の基準

判定は指摘の重要度だけでなく、**マージを止めるべきかどうか**で決める。

- マージ前に修正が必要な例：緊急停止後も API リクエストが続く、API キーがログに出力される、セッションの上限を超えて投稿できる。
- 重要な問題でも、その PR の変更範囲外であれば、後続の課題として `判定：Comment` とすることがある。その場合は、どの Slice で対応するかを明記する。

## 4. 判定が分かれたとき

- 「厳しい判定を採用する」ことは、「厳しい意見が正しい」ことを意味しない。
- まず相違点と根拠を明確にし、必要なら追加のテストで検証する。レビュアー同士の多数決では決めない。
- 二人のレビュアーの判定が一致しても、正しさの証明とはみなさない。同じ設計書を前提にしている以上、同じ見落としをする可能性がある。HTTP スタブによる検証や、失敗を意図的に注入するテストを重視する。

## 5. 実装担当（Codex）への指針

- 判定が `Request changes` の場合、🔴🟠 の指摘をすべて修正してから、再レビューを依頼する。
- 🟡 の指摘は、その PR で対応するか、`docs/implementation-status.md` に後続課題として記録する。
- 設計書で「未決」とされている値や方針（再試行の回数、タイムアウトの秒数など）を、実装の都合で決めない。必要になった場合は PR の説明に論点として書き、設計側の判断を待つ。

## 6. 今後の見直し

正式な GitHub レビュー（レビュアーごとのアカウント分離）とブランチ保護は、開発体制が成熟した段階で導入を検討する。導入した場合は、本規約の 1 と 2 を改める。
